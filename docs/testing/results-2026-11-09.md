# Register recovery verification — 9 November 2026

Scope: recovery after screen/background suspension, network interruption, reload
and expired sessions. Baseline is main revision `a2efcf8`; this report accompanies
the register-recovery change. **Evaluation only; physical-device and other
production gates remain open.** Target event: 21 November 2026.

## Automated results

- **41 tests passed:** six domain, four HTTP helpers, seven register-state,
  twenty service, two concurrency and two API/error-classification tests.
- Next.js self-hosted production build and Vinext hosted build passed. The
  self-hosted build includes TypeScript validation of the application and tests.
- **24 browser tests passed:** twelve scenarios in each of Chromium (Android
  Galaxy Tab S9 layout) and WebKit (iPad layout), using Playwright 1.63.0.
  The final browser run took 22.7 seconds with one worker.

The browser scenarios used a disposable real Next.js/SQLite server. Requests
and responses were deliberately interrupted at defined boundaries:

| Scenario | Verified outcome |
| --- | --- |
| Draft/partial entry, reload and receipt reload | Draft retained; original receipt/change retained after confirmation |
| Reply dropped after server commit | Reload retrieves original receipt; no second sale POST |
| Request dropped before reaching server, tab closed/reopened | Same command ID is resubmitted; one stored sale |
| Offline interval and expired session | Pending command retained; original person logs in; one sale |
| Failure saving acknowledged receipt locally | Original pending command remains; reload retrieves committed receipt |
| Second tab | Waits for ownership; inherits current receipt after first tab closes |
| Unrecorded 409 | Bounded retry retains ID; later pageshow resolves one sale |
| Unclassified 503 | Same behavior; no inference that the sale failed |
| Recorded business rejection | Pending cleared, unbooked basket retained, no financial effect |
| Failure saving the initial intent | No sale request transmitted |
| Interruption immediately after item insertion write | Item appears once in basket; input fields are already cleared |
| Wake/focus while a committed reply remains suspended | Old wait is aborted; original receipt is retrieved without a second sale POST |

The state tests cover interrupted acknowledgement/migration, corrupt storage,
receipt mismatch and stale previous receipts. Service/API tests cover request
fingerprints, actor/event/action mismatch, legacy sale replay, durable rejections,
sale/end-sales races, upgrading existing operation records and transient database
errors returning 503 without exposing SQL details.

## Repeated six-session HTTP workload

The [raw report](results-2026-11-09.json) uses the same methodology as the
[8 November baseline](results-2026-11-08.md): 5,000 fixture sales, then 600 new
HTTP sales across six sessions, five items per sale and a five-cent donation,
plus duplicate replays, full refreshes and restart verification.

All 600 initial sales returned HTTP 200. The final database contained exactly
5,600 sales, unique receipt numbers, 600 new operation/audit records and the
independent expected goods-plus-donation total of **2,835,500 cents**. All 61
replays matched their original results. Integrity and foreign-key checks passed.
Local booking p95 was **386.6 ms**, total workload duration 47.495 seconds.
The browser suite ran concurrently on the same Mac, so this timing is not an
isolated performance comparison or a production SLA.

Runtime: macOS / x64 Node.js 22.23.2, SQLite 3.53.4, 12 logical CPUs and 24 GiB RAM.
No production container quota or portal co-load was reproduced. The synchronized
service characterization happened to complete all ten six-call rounds without
409 in this version. The extra asynchronous hash work changes scheduling;
the unchanged five-attempt server limit has not become a proven capacity guarantee.

## Required field acceptance

These tests do **not** operate an actual tablet lock button, kill an iOS/Android
web process, reproduce venue Wi-Fi or certify storage eviction/power-loss behavior.
Chromium/WebKit emulation is not the installed Chrome/Safari on a chosen device.
Do the [physical-device rehearsal](../operations/register-recovery.md) on all six
registers, then complete the remaining [production gates](../production-readiness.md).
Do not clear browser data or downgrade clients during an event, and do not replay
pending devices into an old restored backup without reconciliation.
