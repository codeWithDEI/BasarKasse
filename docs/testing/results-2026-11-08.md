## Regression and synchronized contention

The regression suite passes 26 tests: six domain, four HTTP-helper, fourteen
service and two new concurrency tests. `pnpm run typecheck` and both production builds
passed separately. The documented SQLite development startup also returned HTTP 200. Tests use local SQLite, not remote D1 or real browsers.

Six distinct service calls were started synchronously in each of ten rounds,
using six tills. **Ten of 60 initial calls returned 409** after the current
five-attempt limit; explicit retries with the original operation IDs completed
all 60. Exact replays returned the same results, receipt numbers were unique and
ledger/operation counts matched. This deterministic schedule demonstrates a real
contention limit. The characterization test reports conflicts while checking financial integrity
with explicit retries; it is not a successful capacity acceptance test.

Six competing payouts for one seller produced one payout and one debit of
850 cents. The resulting till balance was the independently expected 10,150 cents.

## Six-session HTTP run

Command: `LOAD_REPORT=/tmp/basar-load.json pnpm run test:load`, after a self-hosted
production build. Local runtime: macOS, x64 Node.js **22.23.2**, SQLite **3.53.4**,
12 logical CPUs, 24 GiB RAM. There was no production CPU/memory quota, proxy or
venue network. The [raw JSON report](results-2026-11-08.json) is stored alongside this document.
Run timestamp: `2026-11-08T15:53:46.610Z`.

The script used its own temporary server/database; the shared portal demo was
not changed or used for load testing. Historical rows were inserted as fixtures:
5,000 sales / 25,000 items, distributed over six tills. Six authenticated sessions
then each made 100 new sales, five items per sale, a five-cent donation, and a full
state refresh after every sale. Sessions shared the demo cashier identity.

| Observation | Result |
| --- | --- |
| New sale requests | 600 HTTP 200; no failed initial sale requests |
| Duplicate replays | 60 during load plus one after restart; same stored results |
| Measured workload duration | 46.752 seconds |
| New-sale throughput including refresh workload | 12.8 sales/second |
| Booking response p50 / p95 / maximum | 159.3 / 352.4 / 408.8 ms |
| Full-state refresh p95 | 424.3 ms |
| Final snapshot size | 3,980,687 bytes before compression |
| Sales after restart | Exactly 5,600; unique receipt numbers |
| Independent goods-plus-donation total | 2,835,500 cents, matching persisted sales |
| New sale operations / audit rows | Exactly 600 each |
| SQLite integrity / foreign keys | `ok` / no violations |

The different result from synchronized service calls reflects different request
scheduling; it does not invalidate the conflict reproduction. Large full-state
responses are a scaling concern even when loopback traffic is fast.

## Interpretation and remaining evidence

The tested self-hosted HTTP workload preserved accepted sales and replay results
through ordinary server restarts. It does not establish power-loss durability,
zero-loss host recovery, browser crash recovery, six physical devices on Wi-Fi,
remote D1 behavior, actual server quotas/shared portal load or a four-hour soak.
The replay scenario deliberately ignores a received result; it does not drop a
network reply at the instant of commit. Seed history did not include full historic
operation/audit rows. Timing is an observation from one run, not a performance SLA.

The [production gates](../production-readiness.md) remain open. Fix browser/error
recovery and bounded queries, then repeat acceptance on the selected server with
the actual device/network setup and independent full accounting reconciliation.
